# Data model

The intent behind each table; `src/db/schema.ts` is the source of truth for types.

## Why

Wrong numbers here are silent: a length in the wrong unit or a chest measured to a different convention looks plausible and breaks every comparison.
The schema enforces the rules that prevent that structurally.

## How it works

Postgres, every length an **integer mm**, `owner_id` on every table, UUID v7 IDs.

### garment

One row per physical item.

- **Identity:** `category` (enum, drives the measurement template), `subcategory`, `brand`, `name`.
- **Declared colour:** `declared_colour`, the owner's word from `src/lib/colour/declared.ts`.
- **Handle:** `short_id`, per owner, shown as `014`.
- **Cover, denormalised for the grid:** `photo_id` and `cutout_path`; the front, or a shoe's outer side.
- **Not yet used:** `fabric`, `stretch`, `clo`, `windproof`, `waterproof`, `layer_slot`, `layer_index`.

`completed_at` is set by Add to closet, once every shot its kind needs is taken (`src/lib/capture-shots.ts`).
Null means a face is missing or Add was never pressed; the closet lists those as Unfinished.
"To measure" means completed with no measurement rows.

### photo

- `view`: `front`, `back` or `detail` for clothes and belts; `top`, `outer`, `inner`, `toe`, `heel` for footwear.
- Each non-detail view is unique per garment (partial unique index).
- `front`, `back` and `top` must carry a `homography` (check constraint): matrix, px/mm, marker quad, `source` (`sheet` or `a3`).
- A detail has a `detail_kind`: `label`, `fabric`, `print`, `hardware` or `other`.
- `original_path` is kept forever.
  `cutout_path`, `cutout_provider` and `cutout_bounds` (`{x, y, w, h, imageW, imageH}` in original pixels) describe the current cut.
- Reshooting a face replaces it along with its measurements.

### measurement

One row per dimension per garment, on the face the pins were placed on (always the front today).

- **Value:** `key`, `value_mm`.
- **How it was measured:** `is_doubled` and `convention`, recorded from the template's guide and never asked.
- **Where it came from:** `source`: `measured`, `brand_spec` or `estimated`.
- **Pins:** coordinates in that photo's metric canvas.

Derived values (circumference, ease, "fits like") are computed, never stored.

### job

See [Job queue](job-queue.md).

### rig

One row per owner: four sides and the ID 0 to ID 2 diagonal in mm, an optional checking diagonal, the printed black square, and the A3 sheet's black square.
With no row, the `NEXT_PUBLIC_SHEET_*` environment is used.


## Tech

Drizzle with `casing: "snake_case"`; migrations generated by drizzle-kit into `src/db/migrations/`.

## Key files

- `src/db/schema.ts` - tables, enums, constraints
- `src/db/migrations/` - generated SQL, applied by `scripts/migrate.mjs`
- `drizzle.config.ts` - defaults to `localhost:5433`

## Decisions and gotchas

- `is_doubled` and `convention` exist because brands disagree: Standard & Strange double pit-to-pit edge to edge, 3sixteen do neither and measure 1" below the pit.
- Units resolve for display only in `src/lib/units/`.
- The grid picture is the garment's cover, `garment.photo_id`; never test `view === "front"` for it, since a shoe's cover is `outer`.
